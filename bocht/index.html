01 — The framework

One process. No sidecars.

Bocht is a backend framework written as one Bend program. Bend compiles it to C, clang compiles that to a single native binary, and that binary is the whole service: no database process, no reverse proxy, no queue. Everything a request touches lives in the same address space.

Inside the binary · request path1.97 MB · arm64 · builds in ~25 s
Socket
HTTP/1.1 with keep-alive — 100 requests per connection, 64 KB body cap, clean 400/411/413/431 on malformed input.
Auth
Bearer keys scoped to a tenant and a role (admin or member), with rotate and revoke endpoints. No token, no parsing: a 401 comes back before the body is read as JSON.
Limits
Per-credential rate limits, plus separate budgets for key management and admin restarts. Bursts get a 429, not a crash.
Router
20 routes: keys, users, articles, claps, publications, members and an event feed over REST — and POST /mcp for the CMS.
Store
Segmented write-ahead log (64 MiB segments, fsync'd) plus snapshots whose trailer binds the record count and an HMAC. A forged or truncated snapshot is refused at boot.

Honest limits

  • Single node. No replication, sharding or consensus.
  • The log survives the process dying, not the power going out.
  • One request at a time. A slow request blocks every client — which is why the curve in section 04 mattered.
  • Bend moves fast: the builder reports breaking changes in every release from 2.0.18 to 2.0.34, and the pinned r61 release doesn't build on 2.0.34 (confirmed).
02 — The process

Built by one AI. Checked by another.

I didn't write Bocht. I directed an AI app builder that wrote it, and it worked under a verification discipline worth stealing: no claim ships unless it can be re-derived from files on disk.

1 · Probe

Every capability has a script

Each one ends with one canonical line: RESULT: PASS=n FAIL=0. No line, no claim.

2 · Manifest

Results bound to a binary

A stamp script writes the exact binary's SHA-256 next to every result file it produced.

3 · Verify

A second script audits the ledger

Source hash, binary hash, build exit code and manifest must all agree before "done" is written.

4 · Canary

The pinned build is watched

A read-only backup and a hash sidecar are checked hourly against the live binary.

5 · Ledger rule

Never say "flawless"

Verified claims only. Never production-ready, clustered, replicated or bug-free.

What the discipline got right

  • Every hash in the bundle matched its README.
  • The 43-test suite reproduced on a different OS and CPU.
  • By the builder's account, its own first run caught a real protocol bug: the tool name read from the wrong object.
  • Writes survived kill -9: 303 of 303 acknowledged writes, and 20 of 20 single-write cycles.

What it can't see

  • A manifest proves which binary produced a log. It doesn't prove the log tested the right things.
  • All 43 checks used tiny payloads. Nothing timed a realistic post.
  • The suite passed on every version — including the one where a read deleted a post.
  • The shipped verifier needed a ledger file that wasn't in the bundle, so it couldn't be run.
28 Sep · r61 pinned

The framework hardens builder

The builder reports a 200-item hardening campaign landing on release r61: WAL purge tombstones, snapshot HMAC, per-bucket rate limits, keep-alive half-close handling. One of the 200 items ships in the bundle (27 checks, all pass).

29 Sep · morning

The CMS goes on top, additively builder

Per the builder, the MCP blog is appended as one marked section without touching existing lines. It is verified 43/43, then upgraded to Bend 2.0.34 and re-verified.

Round 1 · evaluate

Every claim reproduces. Then the curve. Claude Code

Hashes match, it builds on macOS in 26 seconds, 43/43 passes. Forty extra checks mostly hold — then one timing sweep shows a 16 KB post taking 3 seconds, and a 32 KB post blocking every other client for 33.

Round 2 · the builder's fix

"O(n²) fixed." It wasn't. builder

The "deep fix" removed a depth check from the JSON key finder and skipped several validations. Same speed on the same machine. Seven behaviors changed; one turned a read into a delete. Still 43/43.

Round 3 · the real fix

Profile, fix one function, prove nothing else moved Claude Code

Start again from the version that behaved correctly. Sample the process mid-request, find the hot function, apply the pattern the codebase already uses elsewhere, then replay 90 requests against old and new and diff every byte.

04 — The curve

Double the post, quadruple the wait.

On a log–log chart, a straight line's slope tells you the algorithm. Slope one means time grows with size. Slope two means it grows with the square. The original and the builder's "fix" climb at slope two, steepening further past 32 KB. The fixed build runs at slope one — the same line REST was always on.

Where the time went

Four seconds of macOS sample on the original server while it handled one tools/list request padded to 24 KB. Almost every sample sat in one JSON helper and the string-building it triggered.

jf_raw_go + the frees it triggers52%
String.from_list33%
jf_raw_go (continuation frames)11%
everything else4%

jf_raw_go reads unquoted JSON values like numbers. Every MCP request uses it once, to read the JSON-RPC "id": 1. REST never calls it on a post body, which is why REST stayed fast.

Why a one-character id cost two minutes

In Bend, Bool.pick(cond, a, b) is an ordinary function: both a and b are evaluated before it picks one. So at every character, the helper rebuilt the whole string read so far and kept going — past the end of the number, through the rest of the body.

# before: both branches run at every character Bool.pick(String, jf_raw_end(h), String.from_list(List.reverse(acc)), # O(k) each time jf_raw_go(t, h <> acc)) # never stops # after: carry the stop flag in, match on it (lazy) match hit: case True{}: jf_raw_fin(acc) # built once case False{}: jf_raw_go(t, h <> acc, jf_raw_end(h))

The file already documented this trap and used the fix in its string scanner. This one helper had been missed. 22 lines added, 6 removed.

04b — The builder's fix

Faster on paper. Wrong in practice.

The builder went after the balanced-bracket extractor, not the function that was actually slow. It deleted a depth guard from the JSON key finder, and skipped validations "for performance." Every key lookup started matching the first key with that name at any depth — including in the REST API it had promised not to touch. None of these changed a single test result.

05 — The proof

Same answers. 1,200× sooner.

A speedup is easy to show. Showing that nothing else changed is the part that matters, and a passing suite can't do it — it passed on the broken version too. So the fix was checked against the original, request by request.

06 — Lessons

What 43/43 actually means.

01

A passing suite is a floor, not a verdict.

The suite passed on the original, the regression, and the fix. It measured "still works on small inputs," and was reported as "verified."

02

Evidence binds the file, not the claim.

Hash manifests are excellent at catching drift. They say nothing about whether the right thing was tested, or who ran it.

03

Profile before you fix.

The builder rewrote code that wasn't on the hot path and reported a win. Four seconds of sample named the right function.

04

Diff against a known-good build.

When you have a version that behaves correctly, the strongest test of a change is "same bytes out." Then check the harness can fail.

05

Time one realistic input.

Every functional test used a few bytes. A single 16 KB request — a normal blog post — would have exposed this on day one.

06

Strictness hides in helpers.

In an eager language, a harmless-looking pick(cond, a, b) runs both sides. The codebase knew this, wrote it down, and still missed one.

One AI wrote it. Another checked it. A person decided which one to believe.
